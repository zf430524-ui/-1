# 研学团负责人工作台 v1 SQLite 数据库验收标准

- 文档状态：`DRAFT FOR REVIEW`
- 版本：v1.0
- 编制日期：2026-09-13
- 产品依据：`prd.md`
- 页面依据：`页面字段与交互规则清单.md`
- 全链路依据：`v1端到端验收标准.md`
- 工程依据：`../tasks.md`、`architecture.md`
- 验收对象：负责人本地单端工作台使用的一个 SQLite 数据库文件，以及通过正式服务/API 对它执行的完整业务流程

> 本文不把“建完表”“迁移成功”“接口返回成功”或“某个测试文件通过”视为数据库验收完成。只有同一项目通过正式页面或服务路径完成录入、校验、纠错、联动、导出、重启和备份恢复，且数据库结果与页面和文件结果一致，才能判定通过。

## 1. 验收目标

SQLite 数据库必须同时证明以下五件事：

1. **存得下**：现有产品范围内的学校、导游和项目业务数据能被完整表达，且不引入已排除的资料库和个人明细。
2. **存得对**：必填、状态、唯一性、外键、人数、日期和条件模块约束不会产生非法数据。
3. **改得稳**：跨表保存、批量导入、状态推进、备份恢复失败时不会留下半写入或半恢复状态。
4. **联得动**：班级、老师、导游、司机等源数据变化后，乘车、住宿、用餐、异常、预览和项目状态使用同一口径重新计算。
5. **找得回**：关闭并重启应用后数据仍在；可追查关键操作；备份可校验、可恢复，损坏备份不会覆盖当前数据。

## 2. 范围边界

### 2.1 必须包含

一个 SQLite 文件承载三个逻辑模块：

| 逻辑模块 | 数据对象 | 归属 |
| --- | --- | --- |
| 学校库 | 学校、学校联系人 | 跨项目复用 |
| 导游库 | 导游、受控证件引用、带团事实、退团事实 | 跨项目复用 |
| 项目业务数据库 | 项目、班级、老师、项目导游、项目随团人员来源、乘车、住宿、用餐、导入、导出、异常、操作日志 | 归属于具体项目 |

### 2.2 明确不包含

出现下列任一内容，直接判定范围验收失败：

- 学生姓名、学生身份证号或学生个人名单表。
- 银行卡、银行账户或结算账户字段。
- 跨项目复用的车辆库、司机库、酒店库、房间库、餐厅库。
- 在住宿或用餐模块中另建一套工作人员姓名档案或人数基数。
- 微信群读取、自动发群、在线报名、导游移动端相关数据。
- 浏览器 `localStorage` 作为正式业务数据源，或三个互相独立的 SQLite 文件。

### 2.3 文件不直接塞入数据库

- 导游证件图片保存在受控证件目录，数据库只保存受控引用和脱敏信息。
- Excel 保存在导出目录，数据库只保存生成记录、数据版本和结果。
- 备份保存在独立受限目录，不与普通导出混放。

## 3. 状态与总判定

| 状态 | 含义 |
| --- | --- |
| `NOT_RUN` | 未执行，不能写“基本可用” |
| `PASS` | 步骤、业务结果、数据库断言和证据全部符合 |
| `FAIL` | 已执行但结果不符，必须记录实际值和复现步骤 |
| `BLOCKED` | 缺少明确外部条件，写明负责人和解除条件 |
| `REVIEW` | 机器结果通过，但真实样表、Windows 权限或负责人业务判断未完成 |

数据库总验收只能在以下条件全部满足时为 `PASS`：

1. DB-PRE 全部通过。
2. DB-SCHEMA、DB-TX、DB-SEC 全部通过。
3. DB-FLOW-01 至 DB-FLOW-12 使用同一个主项目 ID 跑通；条件分支可以使用隔离副本或补充项目，但不得替换主项目绕过错误。
4. 页面、正式 API、SQLite 查询、Excel 回读四方结果一致。
5. 所有故意制造的错误都能被拒绝或形成可定位异常，修正后能重新通过。
6. 重启持久化和备份恢复均实际执行，不以“已经生成备份文件”代替恢复验证。
7. 自动证据、浏览器证据和负责人业务复核均齐全。

任一关键项未执行时，总状态不得为 `PASS`。某一纵向子流程已通过，只能标记该子流程 `PASS`，不能推导整个数据库已完成。

## 7. 数据库结构与迁移验收

### DB-SCHEMA-00：运行参数

每次正式打开数据库后必须自动核对：

- `PRAGMA foreign_keys` 为 `1`。
- `PRAGMA journal_mode` 为 `wal`（纯内存测试库除外）。
- `PRAGMA busy_timeout` 为 `5000`，或后续经评审批准的明确值。

不能依赖验收人员手工执行 PRAGMA 后才通过。

### DB-SCHEMA-01：全新建库

**操作**：删除专用验收目录中尚未使用的空数据库文件，执行正式迁移命令，再启动应用。

**必须通过**：

- 自动创建数据库目录和一个 SQLite 文件。
- `schema_migrations` 按版本升序保存每次迁移，版本号不重复。
- 当前代码下应落到版本 6；以后新增迁移时，以代码中最新版本为准，不固定伪造结果。
- `PRAGMA integrity_check` 返回 `ok`，`PRAGMA foreign_key_check` 返回 0 行。
- 应用能正常解锁并读取空状态。

**失败条件**：需要手工补列、手工插入版本号、忽略迁移错误后才能启动，或产生多个业务数据库文件。

### DB-SCHEMA-02：重复迁移和升级失败保护

**操作**：同一数据库连续执行两次迁移；另在隔离副本中制造一条必然失败的测试迁移。

**必须通过**：

- 第二次正常迁移不重复建表、不重复加列、不改变业务数据。
- 失败迁移整体回滚，不写入对应 `schema_migrations` 版本。
- 失败后旧版本数据库仍可按既定回滚方案打开，或明确安全拒绝启动，不能半升级运行。

### DB-SCHEMA-03：表、关系与范围

**操作**：读取 `sqlite_master` 和外键清单。

**必须通过**：

- 学校/联系人、导游/证件/事实、项目/班级/老师/项目导游、项目车辆司机、乘车/住宿/用餐、导入/导出/异常/日志对象均可表达。
- 项目业务行可追溯到项目；班级和项目导游可追溯到稳定 ID，不依赖姓名作为关联键。
- 历史引用采用 `RESTRICT` 或等价保护；只属于父记录的临时/明细行才允许受控级联删除。
- 不存在第 2.2 节禁止的表和字段。

### DB-SCHEMA-04：数据库级约束

至少用自动测试覆盖以下拒绝行为：

- 同名学校、同一学校两个默认联系人。
- 项目结束日期早于开始日期；一日游却启用住宿；不含餐却有正餐次数。
- 班级总人数不等于男生加女生；同一项目班级重名。
- 非法性别、非法合作状态、非法项目状态、非法导入/异常/日志状态。
- 车辆/房间/桌数容量小于等于 0；分配人数小于等于 0。
- 同项目车号重复、同入住日房号重复、同餐次桌号重复。
- 创建指向不存在学校、项目、班级、导游或父行的孤儿记录。

被拒绝后需证明相关表计数和原数据均未变化。

## 8. 事务、数据访问和并发边界验收

### DB-TX-01：跨表原子保存

对“学校+联系人”“项目+班级+老师”“导入批次+正式写入”“安排+异常更新”分别执行一次故障注入：让第 N 条写入失败。

**通过标准**：整个事务回滚；不能出现主表已写、明细缺失，或正式数据已写、批次仍显示待确认的状态。

### DB-TX-02：参数化和统一入口

**通过标准**：

- 页面脚本不包含 SQLite 调用或拼接 SQL。
- 数据访问层查询使用参数绑定；带引号、分号和 SQL 关键字的普通文本只作为数据保存。
- 写操作由服务层执行格式、关联和业务校验，不能只依赖页面校验。
- 返回结果明确区分成功、部分成功和失败；失败响应不泄露绝对路径、SQL、完整证件值。

### DB-TX-03：锁等待和重复提交

**操作**：在隔离测试中占用写事务，并在 5 秒内发起第二次写入；对保存、确认导入和备份按钮模拟重复提交。

**通过标准**：等待或明确失败，不产生重复项目、重复导入、重复安排或损坏库；页面收到可理解结果。超出 busy timeout 时必须回滚并可重试。

## 9. 必须跑通的数据库业务流程

每个流程都必须执行“正常写入 → 故意制造异常 → 证明未误写或形成异常 → 修正 → 重查数据库 → 检查下游”。只做正常路径不算通过。

### DB-FLOW-01：学校库到项目引用

1. 通过 P13 新增学校和一个默认联系人，搜索后可查。
2. 新增疑似同名学校，必须提示并等待人工确认，不静默合并。
3. 建立主项目时带入默认联系人副本；修改项目联系人，学校联系人不改变。
4. 停用学校，历史项目仍保留关联；尝试硬删除被引用学校必须失败。
5. 数据库核对学校 1 条、默认联系人 1 条、项目 `school_id` 正确，无年级/班级写入学校库。

### DB-FLOW-02：项目、班级、老师和人数约束

1. 通过 P03 用最少字段创建主项目，记录实际 `project_id`；补充住宿、用餐和联系人资料，刷新后仍存在。
2. 通过 P05/正式导入建立 3 个班和 5 名老师。
3. 故意把 801 班总人数改为 41，而男 22 + 女 20。错误行可以保留在导入临时区供修正，但正式 `classes` 表写入必须被拒绝，原 42 人记录保持不变；系统不得静默改写任一数字。
4. 修正为 42，数据库得到学生 125、男 63、女 62、老师 5、所需导游 3。
5. 关闭并重启应用，按同一项目 ID 查询，数据保持一致。

### DB-FLOW-03：导入临时区到正式表

对学校、班级老师、接龙、车辆、住宿资料分别执行：

1. 解析后只写 `import_batches`、`import_rows` 和隔离文件引用；确认前正式业务表计数不变。
2. 人工映射、修改预览值、跳过重复/错误行后，页面显示预计新增、更新、跳过、失败数量。
3. 选择“全部正确才导入”时，只要一行错误，整批正式表 0 写入。
4. 选择“仅导入有效行”时，只写有效行，批次为“部分成功”，失败行和原因保留。
5. 更新既有对象时，空值不覆盖原有非空值。
6. 相同来源重复提交被识别，不重复写正式表。
7. 取消未完成批次时清理临时行和临时文件，同时保留必要审计事实。
8. 未注册正式写入适配器的目标安全拒绝，不能显示“导入成功”。

### DB-FLOW-04：导游匹配、日期冲突、分班和历史事实

1. 建立 6 名脱敏导游和一个冲突参照项目；接龙原文、原始序号 1—6 和批次必须保留。
2. 只有姓名与手机号同时一致才自动匹配；同名不同号、同号不同名、缺手机号、未建档均进入人工确认。
3. 日期冲突、证件过期或合作停用的导游分配必须被拒绝，数据库不得出现其 `assigned_class_id`。
4. 3 名合格导游分别绑定 801、802、803 班；默认一人一班。显式双班例外必须有原因。
5. 记录退团时保存原因、时间、距出团天数和替换关系；退团释放班级并形成缺口，替换后重新检查冲突。
6. 被历史项目引用的导游不能硬删除；停用后历史项目仍可读取当次事实，但新项目不能再安排。

### DB-FLOW-05：统一项目随团人员来源

1. 查询统一人员来源，老师、项目导游、项目司机和手工角色分别带有来源类型、来源 ID、性别、住宿人数和默认就餐人数。
2. 退团、替换、司机修改、老师参与标记修改后，统一来源立即变化，不残留旧来源。
3. P09/P10 的工作人员汇总必须由该来源读取；若两页存在独立可编辑工作人员基数，本流程失败。
4. 最终得到老师 5、导游 3、司机 3，住宿和每餐工作人员均为 11 人。

### DB-FLOW-06：乘车安排与容量纠错

1. 导入 3 辆项目车辆及司机，不创建跨项目车辆或司机档案。
2. 录入三班学生、5 名随车老师和 3 名导游，最终乘车人数为 133。
3. 将 3 号车容量改为 47；必须得到乘车 48、空位 -1、超载 1 的阻断异常，且项目不能完成、乘车表不能正式导出。
4. 改回 49，阻断关闭；总座位 147、空位 14。
5. 把 803 班增加 1 人，乘车校验和旧预览立即失效；恢复后重新校验。
6. 补充分支验证一班拆两车后，各车学生合计等于原班人数，不能因拆车重复计算老师或导游。

### DB-FLOW-07：条件住宿和分房纠错

1. 主项目启用住宿后才允许创建房间和分房记录；房源仅属于当前项目。
2. 导入 35 间四人房，总容量 140；从统一人员来源计算住宿 136、男 69、女 67。
3. 安排结果不得超员、漏人或男女混住；跨班拼房保存双方班级、人数和原因。
4. 故意把 1 名男老师放入女性房，必须产生阻断，住宿导出不可用；移回后异常关闭。
5. 新建一日游且不住宿的补充项目，住宿入口为不适用；住宿相关表对该项目均为 0 行，也不产生空住宿导出记录。
6. 从“需要住宿”改为“不需要”时，若已有记录必须显示影响并二次确认；取消或失败时原数据不变，确认清理时在一个事务内完成并留痕。

### DB-FLOW-08：条件用餐和桌数纠错

1. 主项目建立两餐，两家餐厅、桌号和统计互不串扰；餐次在项目日期内。
2. 每餐从统一来源得到 136 人；学生 + 导游 128 人的基础建议为 13 桌，老师 + 司机 8 人单列，最终 14 桌、容量 140、余位 4。
3. 只建 13 桌且漏掉工作人员时，必须产生未安排或容量不足阻断。
4. 同餐桌号重复必须被数据库唯一约束或服务校验拒绝；修正后关闭异常。
5. 单餐参加人数偏离默认值时，必须保存差异人数和原因，重新计算该餐，不影响另一餐。
6. 新建不含餐补充项目，用餐相关表为 0 行，也不产生空用餐导出记录。

### DB-FLOW-09：异常、重算和项目状态门禁

1. 超载、混住、桌数不足等问题必须保存为可定位异常，包含项目、模块、等级、来源类型、来源 ID 和稳定指纹。
2. 同一问题重复校验不新增重复行；修复源数据后原异常转为已解决，而不是无记录消失。
3. 阻断异常不能手工确认例外；警告/提醒确认例外必须填写原因。
4. 有未解决阻断时，推进“已完成安排”必须失败，数据库状态不变。
5. 无阻断且所有适用模块完成时才可进入“已完成安排”。
6. 完成后修改班级人数、导游、车辆、住宿或用餐，项目自动退回“待检查”，并使受影响旧预览过期。

### DB-FLOW-10：预览、Excel 和数据版本

1. 保险、乘车为固定输出；住宿、用餐只在适用项目出现。
2. 预览直接读取项目当前数据，不建立可编辑的第二套业务表。
3. 源数据变化后，旧预览或导出数据版本必须过期，旧版本不得继续导出。
4. 文件写入临时位置、校验成功并原子完成后，`export_records` 才能记为成功。
5. 用 Excel 实际打开并程序化回读四类适用文件；字段、中文、项目 ID 和第 6.3 节合计一致。
6. 导出失败记录失败原因，不能产生成功记录；无业务数据不生成空文件。

### DB-FLOW-11：审计、脱敏和历史保留

1. 导入、查看敏感资料、修改安排、导出、备份、恢复六类操作均至少产生一条日志，失败操作也有失败记录。
2. 日志记录时间、类型、对象、对象 ID、变更摘要、结果和失败原因，可按项目和结果查询。
3. 日志仓储和普通 API 不提供编辑或删除能力。
4. 对数据库、API 响应和页面日志扫描，完整身份证号、导游证号和证件绝对路径出现次数必须为 0。
5. 已结束项目的关联和当次安排事实保持可读；后续修改基础档案不应改写历史项目事实。

### DB-FLOW-12：重启、备份、损坏拒绝和恢复

1. 完成主项目关键数据后正常关闭数据库和应用，再启动并按同一项目 ID 核对第 6.3 节数据。
2. 创建包含 SQLite 与证件目录清单的备份；核对文件存在、大小、SHA-256、清单一致和 SQLite 完整性。
3. 备份后写入唯一临时标记并确认可查。
4. 恢复时输入备份编号二次确认，默认先生成受保护的当前状态副本；恢复后临时标记消失，主项目 ID 和备份时数据一致。
5. 损坏数据库文件或清单后再次恢复，必须被拒绝；当前数据库和证件目录逐项不变，并留下失败日志。
6. 构造超过 30 个日备份和 12 个按月代表的隔离样本，轮转结果正确；归档副本和最新可用备份不被删除。
7. 模拟清理旧备份失败，新备份仍存在且可校验。

## 10. 安全与完整性验收

### DB-SEC-01：本机和会话边界

- 未解锁业务 API 返回拒绝；退出或进程重启后旧会话失效。
- SQLite、证件和备份路径不通过普通页面或错误响应暴露。
- 服务固定监听 `127.0.0.1`，数据库文件不通过静态目录下载。

### DB-SEC-02：Windows 目录权限

在计划录入真实敏感资料前，必须由公司目标 Windows 账户现场验证：

- 负责人账户可读写数据库、证件和备份目录。
- 无关普通账户不能读取或复制这些目录。
- 应用可正常备份和恢复，不因 ACL 造成静默缺文件。

该项未现场完成时，机器测试即使全绿，真实业务试用状态最高为 `REVIEW`，且只允许模拟或脱敏数据。

### DB-SEC-03：运行中完整性

正式验收开始、主流程结束、恢复结束三个时间点都必须执行：

```sql
PRAGMA integrity_check;
PRAGMA foreign_key_check;
```

通过标准分别为 `ok` 和 0 行。任何一个时间点失败，总验收立即为 `FAIL`。

## 11. 自动检查与人工执行要求

### 11.1 当前可执行命令

```powershell
npm.cmd run check
npm.cmd run test:integration
npm.cmd run test:e2e
npm.cmd run test:database
```

这些命令是进入正式验收的基线，不代替第 9 节完整业务流程。

### 11.2 最终自动化门禁

在 T12—T29 完成前，开发必须把 DB-FLOW-01 至 DB-FLOW-12 的关键正常、异常、回滚和联动断言纳入自动测试，并提供一个稳定的单命令入口。该入口必须：

- 创建独立临时目录和全新数据库。
- 自动迁移、构造脱敏数据、执行正式服务/API，不绕过业务层直接造最终结果。
- 在结束时运行完整性、外键和敏感信息检查。
- 测试失败返回非 0，并保留失败场景和实际值。
- 不读取或覆盖默认 `.runtime` 中可能存在的业务数据。

单命令入口在仓库中真实存在并运行成功后，才能写入验收记录；不能只在文档中约定一个尚不存在的命令并声称通过。

### 11.3 人工流程门禁

至少在 1366×768 目标办公环境中通过页面执行一次主流程，重点人工判断：

- 错误能否定位到应该修改的对象。
- 修正后下游是否自动更新，而非依赖刷新示例数据。
- 条件模块是否真正不建记录、不导空表。
- 备份和恢复的覆盖影响、二次确认是否清楚。
- Excel 是否能直接用于负责人复核。

## 12. 必须保留的验收证据

| 证据类型 | 最低要求 |
| --- | --- |
| 版本 | 提交号/包哈希、Node.js 和 SQLite 版本、执行日期 |
| 路径 | 验收数据库、证件、导入、导出、备份绝对路径 |
| 命令 | 完整命令、退出码、测试数量和原始输出 |
| 数据库 | 迁移版本、三次完整性检查、外键检查、关键表计数和最终聚合值 |
| 流程 | 每个 DB-FLOW 编号的操作、实际结果、状态、缺陷编号 |
| 联动 | 每次异常产生、源数据修正、异常关闭、预览过期和状态回退前后对照 |
| 文件 | Excel 文件名、大小、SHA-256、程序化回读和实际打开截图 |
| 恢复 | 备份编号、清单、哈希、恢复前后项目 ID 和关键数据对照 |
| 安全 | 未授权拒绝、监听地址、敏感扫描、Windows ACL 现场结果 |

页面显示“保存成功”“导出成功”或“恢复成功”只能作为辅助证据；没有数据库、文件或恢复后查询结果，不得判定通过。

## 13. 一票否决项

出现下列任一情况，数据库总验收直接为 `FAIL`：

- 主流程中更换项目、删除重建项目或直接改 SQLite 来绕过业务错误。
- 页面、数据库、异常、Excel之间的人数或状态不一致。
- 事务失败后留下半写入；恢复失败后留下半覆盖。
- 外键未启用、存在孤儿记录、`integrity_check` 非 `ok`。
- 同一导游冲突分配或重复分班且无显式例外。
- 车辆超载、住宿混住/超员/漏人、用餐桌数不足仍能推进完成或导出成功。
- 不适用的住宿/用餐项目仍创建空业务记录或空导出。
- 源数据变化后旧预览仍能直接导出。
- 日志或响应泄露完整证件值、证件绝对路径。
- 损坏备份能够覆盖当前数据，或备份从未实际恢复验证。
- 引入学生个人名单、银行卡或跨项目车辆/酒店等超范围数据结构。

## 15. 完成定义

“SQLite 数据库完成”必须同时表示：

- 数据模型符合已批准范围。
- 迁移、约束、事务、日志、重启和备份恢复通过。
- 同一个主项目跑通学校 → 项目 → 班级老师 → 导游 → 车辆 → 住宿 → 用餐 → 异常 → 状态 → Excel → 恢复。
- 每个模块至少验证一次失败、拒绝或异常修正路径。
- 所有适用页面、数据库和 Excel 关键数字一致。
- 有完整证据，并由负责人完成业务可用性复核。

少任何一项，都只能写“某一子任务已完成”或“当前自动测试通过”，不能写“SQLite 数据库已验收完成”。
