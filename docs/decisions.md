# 关键决策记录

## D001 · 产品方案基线

- 状态：已确认
- 决策：采用第一次业务梳理作为产品主线，保留导游、车辆、住宿和表格输出的完整业务框架。
- 理由：最贴近现有旅行社工作方式，也能覆盖后续履约细节。

## D002 · 原型技术形态

- 状态：待 PRD 确认后复核
- 候选决策：使用零依赖的 HTML、CSS 和原生 JavaScript 单页应用，Node 仅用于本地静态服务和自动测试。
- 理由：此前环境发现没有 npm，零依赖方案可快速运行和验证。
- 复查条件：生成正式开发任务前重新检查工作区与运行环境；进入多人联网试用时必须迁移到带后端和数据库的架构。

## D003 · 原型数据存储

- 状态：候选，等待 PRD 确认
- 决策：原型数据保存在浏览器 `localStorage`，示例数据与领域逻辑分离。
- 限制：不可用于真实身份证、导游证照片或号码等敏感资料。
- 迁移条件：真实试用前接入服务端数据库、对象存储、登录权限和审计日志。

## D004 · 招募与锁档

- 状态：候选，等待 PRD 确认
- 决策：采用“导游报名 → 工作人员录取 → 导游确认 → 正式锁档”。
- 理由：兼顾导游自主报名与旅行社统筹权，并防止未最终确认的报名长期占档。

## D005 · 自动编排定位

- 状态：已确认
- 决策：车辆与住宿均采用“系统建议＋人工调整＋持续校验”，不承诺无人值守的最终方案。
- 理由：真实业务存在车型、熟悉度、楼层、教师房等大量例外。

## D006 · 外部服务边界

- 状态：已确认
- 决策：微信、保险与未来通知服务必须放在独立适配边界，核心业务不依赖具体供应商。
- 原型替代流程：复制招募文案、模拟分享链接和导出结构化资料。

## D009 · 退出与信用处理

- 状态：候选，等待 PRD 确认
- 决策：已确认导游退出采用申请—审批—补位并保留原因；首版不自动扣分或限制抢团。
- 理由：先保留客观事实，避免在申诉和纠错机制缺失时自动惩罚。

## D010 · 车辆安全余座

- 状态：候选，等待 PRD 确认
- 决策：安全余座按项目配置，默认 0；车辆恰好坐满时提示，不视为超载。
- 理由：用户样表中存在 0 空车位，不能武断设置固定余座。

## D011 · 表格复刻标准

- 状态：候选，等待 PRD 确认
- 决策：v1 验收字段、合计和业务结构一致，不承诺逐单元格或像素级一致；获得原始可编辑工作簿后在 v1.1 单独实现模板级导出。

## D012 · 住宿版本边界
