# 研学派团工作台 PRD

- 版本：v1.0 候选版
- 状态：REVIEW（等待产品确认）
- 更新日期：2026-09-05
- 产品基线：用户确认的第一版业务思路

## 1. 背景与问题

春秋研学旺季常出现“团多、导游少”的资源紧张情况。现有流程主要依赖微信群接龙和多份 Excel：旅行社发布招募信息，兼职研学导师自行报名；人员确定后再建立项目群，逐项发布集合、班级、老师、车辆、司机和住宿信息。

这种方式存在四类核心问题：

1. 同一导游可能在日期重叠的项目中重复确认。
2. 报名、录取、退出和补位缺少统一状态与留痕。
3. 班级、车辆、司机和住宿信息被重复整理，容易漏项或超载。
4. 证件资料、保险名单和最终执行表分散，人工核对成本高。

## 2. 产品目标

以“一次研学项目”为中心，统一管理导游招募、人员锁档、班级编排、车辆匹配、住宿分配和执行表输出，在保留人工最终决定权的前提下，减少重复录入和低级错误。

### 2.1 v1 成功标准

- 导游确认时能自动阻止全部日期重叠的重复锁档。
- 车辆方案不超核定可用座位；资源不足时能定位未安排班级和缺少座位。
- 住宿方案不超房间容量，男女分开，跨班拼房被醒目标记。
- 项目负责人能从同一项目生成可执行的乘车安排和人员资料清单。
- 关键状态变化可追溯到操作时间、操作对象和原因。

### 2.2 试用期建议观测指标

- 单个项目从资料齐备到发布执行表的平均耗时。
- 人工重复录入次数和发布后返工次数。
- 日期冲突、车辆容量不足、资料缺失等问题被系统提前发现的数量。
- 已确认导游临时退出率与补位平均耗时。

首版不预设硬性提升比例；用 3—5 个真实项目建立基线后再设目标。

## 3. 用户与权限

| 角色 | 主要职责 | v1 权限 |
| --- | --- | --- |
| 旅行社负责人/管理员 | 创建项目、发布招募、录取导游、编排车辆住宿、发布执行信息 | 管理全部项目数据；查看资料完整状态；导出名单和执行表 |
| 调度工作人员 | 协助报名审核、班级/车辆/住宿维护、异常处理 | 操作被授权项目；不管理系统级设置 |
| 兼职研学导师 | 查看可报名项目、报名、确认、查看本人日程、申请退出 | 仅查看允许公开的项目信息和本人相关数据 |

原型阶段不实现正式登录和权限隔离，以角色视图和模拟数据验证流程；真实试用前必须接入认证、授权和审计。

## 4. 产品边界与版本范围

### 4.1 v1 可交互原型

- 管理端桌面工作台：首页、项目、招募、导游、车辆、住宿、表格与异常中心。
- 导游移动端关键流程：查看招募、报名、候补、确认、查看本人日程、提交退出申请。
- 本地示例数据和浏览器本地持久化，仅用于演示与规则验证。
- 乘车安排表支持预览与结构化 CSV 导出。
- 住宿支持手工录入房间、系统建议、人工调整、校验和预览。
- 证件模块仅使用脱敏模拟字段和“资料是否完整”状态，不保存真实证件图片或号码。

### 4.2 v1.1

- 房源与名单批量导入。
- 完整住宿自动分配、异常处理和分房表导出。
- 根据用户提供的可编辑原始模板，制作更接近现有样表的 Excel 导出。

### 4.3 明确不做

- 不读取或控制微信群，不开发微信机器人。
- 不直连保险购买接口，只准备结构化人员资料清单。
- 不提供学校、车队、司机独立账号。
- 不处理工资结算、在线支付或发票。
- 不做多旅行社 SaaS 租户体系。
- 不保存学生姓名或身份证，只保存班级聚合人数。
- 不按学校“好坏”或年龄段自动给导游抢团优先级；首版只记录可解释的业务事实。
- 不把自动建议当作最终安排，所有发布结果须由工作人员确认。

| 导游 | 姓名、电话、常住区域、资料完整状态、可用日期、合作备注 |
| 招募 | 项目、所需人数、公开说明、截止时间、报名与候补队列 |
| 派团记录 | 项目、导游、岗位/班级、报名状态、确认时间、退出与替换关系 |
| 车辆 | 车型、核定座位、项目可用座位、车牌、所属车队、状态 |

| 活动记录 | 操作人、时间、动作、对象、变更摘要、原因 |

## 6. 核心流程

### 6.1 创建项目与准备资料

负责人创建项目，维护学校、年级、日期、班级人数、教师、集合信息和负责人。系统校验班级总人数必须等于男生数与女生数之和，并汇总项目总人数。

### 6.2 导游招募与锁档

1. 负责人设置所需导游数量、报名截止时间和导游可见信息并发布。
2. 导游报名；名额达到上限后，新报名自动进入候补。
3. 工作人员审核并录取；录取不立即锁档。
4. 导游确认时，系统检查其已确认项目的完整日期区间。
5. 无冲突则确认并锁档；有冲突则阻止确认并显示冲突项目。
6. 确认后退出需提交申请，负责人批准并从候补或导游库补位。

### 6.3 班级与车辆编排

负责人导入或维护车队、车型、可用座位、车牌和司机。系统按“一班一车优先、不得超载、尽量少空座”生成建议；资源不足时不强行生成完整方案，而是列出缺口。人工调整后系统重新校验。

### 6.4 多日项目住宿编排

负责人录入酒店和房间容量，系统按男女分开、不得超容量、尽量少跨班拼房生成建议。人工调整后持续校验；跨班拼房、未分配人数和容量冲突均需突出显示。

### 6.5 发布与输出

负责人完成校验后发布执行信息。乘车安排至少包含项目标题、学校负责人、总领队、车号、导游、班主任、配班老师、班级、学生人数、随车老师、车辆空余、车型、车牌、司机电话和备注。住宿表至少包含班级、总人数、男女人数、房号、各房人数、拼房关系和合计。

## 7. 功能需求

### 7.1 首页

- 显示近期项目、各状态数量、待确认导游、车辆/住宿缺口和待处理退出申请。
- 可按日期、学校、项目状态筛选，并进入对应项目或异常详情。

### 7.2 项目管理

- 创建、编辑、复制和取消项目。
- 维护班级、教师、集合和负责人信息。
- 显示资料完整度和进入下一阶段前的缺项。

### 7.3 招募与导游侧

- 生成可复制的招募文案和模拟分享链接。
- 支持报名、审核、录取、候补、确认、退出申请、批准、替换和完成。
- 导游可见信息默认包括学校、年级、日期、集合时间与地点、行程天数、岗位说明和注意事项；不显示其他导游资料或内部评价。
- 导游确认前必须再次展示日期和集合信息。

### 7.4 导游档案

- 维护联系方式、常住区域、可用日期、合作备注和资料完整状态。
- 证件号在生产版默认脱敏展示，证件图片须单独授权访问。
- 可生成保险所需资料清单；原型只导出模拟数据。

### 7.5 车辆与司机

- 维护车型、核定座位、项目可用座位、车牌、司机和联系方式。
- “安全余座”是项目级可配置项，默认 0；坐满时提示但不判定为错误。
- 自动建议默认一班一车；多班同车只能人工调整，并醒目标记。

### 7.6 住宿

- 仅对两天及以上项目启用。
- v1 支持手工房源、建议、拖动/选择式调整、容量和性别校验、拼房标记与预览。
- v1.1 再支持批量导入、完整导出和更复杂的教师房规则。

### 7.7 表格与异常中心

- 输出字段、合计和业务结构与用户样表保持一致；v1 不承诺逐单元格或像素级复刻。
- 若需模板级 Excel 复刻，须取得原始可编辑工作簿并在 v1.1 单独验收。
- 异常按阻断发布、需确认、提示三级展示。
- 批量操作返回成功、部分成功或失败；部分成功必须列出每一失败项及原因。

## 8. 状态与规则

### 8.1 项目状态

草稿 → 招募中 → 待确认 → 人员已齐 → 编排中 → 已发布 → 执行中 → 已完成。

任一执行前状态可取消；已发布后变更须产生提醒和活动记录。

### 8.2 报名状态

已报名 → 待审核 → 待确认 → 已确认 → 已完成。

分支状态包括候补、未录取、退出申请中、已退出、已替换和爽约。已确认状态才正式占用日期；退出批准后释放日期并保留记录。

### 8.3 业务校验

1. 多日项目占用开始至结束日期的完整闭区间。
2. 日期包含、交叉、同日起止均视为冲突。
3. 车辆乘员数包含学生、教师、导游和其他随车人员。
4. 项目可用座位 = 核定座位 − 项目安全余座；不得为负。
5. 房间不得超容量，男女不得混住；教师房例外规则后置到 v1.1。
6. 自动建议后允许人工修改；每次修改后重新校验。
7. 系统不得根据不可解释或带歧视性的个人偏好自动分配工作。

## 9. 退出、替换与信用记录

- v1 推荐规则：已确认导游提交退出原因，负责人批准后释放档期。
- 系统记录申请时间、批准时间、原因和替换关系。
- 首版不自动扣分、不自动限制抢团；负责人可记录事实性合作备注。
- 若未来建立信用机制，须另行定义申诉、有效期、可见范围和人工纠错规则。

## 10. 数据、隐私与安全

- 原型仅使用模拟或脱敏数据，禁止录入真实身份证号、导游证号和证件照片。
- 生产版需具备登录、最小权限、敏感字段加密、图片对象存储、访问日志、备份和删除机制。
- 证件号默认只显示末四位；导出敏感资料须记录操作者、用途和时间。
- 学生数据保持班级聚合，不采集不必要的个人信息。

## 11. 非功能要求

- 1366×768 及以上桌面视口可完成管理端核心操作，无页面级横向溢出；宽表可在表格容器内滚动。
- 390×844 移动视口可完成导游报名、确认、查看日程和退出申请。
- 常规列表、筛选和校验在本地示例数据规模下 1 秒内反馈。
- 所有阻断性错误使用文字说明，不能只依赖颜色。
- 刷新页面后原型数据保留，并提供恢复示例数据入口。

## 12. 验收标准

1. 能创建含多个班级的项目，并正确校验班级和项目人数。
2. 导游报名、候补、录取、确认、退出和补位均可完成且状态可追溯。
3. 日期冲突测试覆盖同日、交叉、包含和多日相邻不冲突。
4. 车辆建议不超可用座位；不足时显示未安排班级和缺少座位数。
5. 人工改变车辆后立即重新计算余座和冲突。
6. 多日项目能生成不超容量、男女分开的住宿建议；跨班拼房和未分配人数可识别。
7. 乘车安排预览包含约定字段与合计，CSV 可被 Excel 正常打开且中文不乱码。
8. 首页统计与项目、人员、车辆和异常数据一致。
9. 管理端和导游端在目标视口完成关键流程，键盘可访问主要操作。
10. 原型中不存在真实证件数据，也不声称已完成微信、保险或云端接入。

## 13. 风险与依赖

- Figma Starter MCP 写入额度已触顶；当前以已确认的本地预览图作为视觉基准，额度恢复后再补 Figma 画板。
- 现有两张参考表是图片，无法验证公式、合并单元格和打印参数；精确导出依赖原始工作簿。
- 不同旅行社对锁档、退出和安全余座规则可能不同，应保留配置能力。
- 真实证件存储涉及个人信息保护，不能沿用本地原型方案。

## 14. 待确认后冻结的产品决策

本候选版采用以下推荐默认值，需用户一次确认后进入 `APPROVED`：

1. 导游报名时可见学校、年级、日期、集合信息、行程天数、岗位说明和注意事项。
2. “工作人员录取＋导游确认”后正式锁档。
3. 已确认退出采用申请—审批—补位，首版只记录、不自动扣信用分。
4. 车辆安全余座项目级可配置，默认 0，坐满仅提示。
5. v1 输出保持字段、合计和业务结构一致，不承诺像素级复刻；模板级 Excel 放到 v1.1。
6. v1 包含住宿基础流程，批量导入和完整分房表导出放到 v1.1。
